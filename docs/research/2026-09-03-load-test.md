## 2. 시나리오별 상세

### (a) join.js — 30초 200명 입장

```
join_latency ........ avg=149ms min=114 med=122 p90=234 p95=283 p99=411 max=466   (200/200 성공)
ws_connecting ....... avg=0.99ms p95=3.6ms
participants_frames . 36,260   (입장 1건당 접속 중 전원에게 1프레임 → 200명 입장 시 ≈ n²/2 = 20,000 + 유지 구간 중복)
ws_msgs_received .... 37,260 (1.4MB)
서버 CPU ............ avg 3.9% p95 14.3% max 20.4%   RSS 143.8 → 164.8MB
```

- `student:join` 핸들러가 `await persistParticipant()`(Supabase 왕복) 뒤에 `joined` 를 보내므로 join 지연의 대부분(≈110ms)은 DB 왕복이다. 400명이면 PostgREST 처리량이 먼저 한계가 온다(현황 문서 §2.4 A).
- `participants` 브로드캐스트가 입장 수의 제곱으로 늘어난다. 200명에서 36k 프레임/50초라 아직 가볍지만 1,000명이면 ~50만 프레임. p2-core 의 배치(500ms 스로틀)가 이를 상수로 만든다.

### (b) vote.js — 200명이 10초 안에 워드클라우드 투표

```
join_latency ........ avg=116ms p95=180ms
vote_ack_latency .... avg=4.5ms med=4 p90=9 p95=11 p99=13 max=13   (200/200 성공)
poll_settle_ms ...... 10.0s (= VOTE_WINDOW → 마지막 표가 들어온 직후 전원 total=200 관측, 처리 적체 없음)
poll_update_frames .. 40,200 (= 200표 × 201소켓, O(n²))   ws_msgs_received 61,803 (5.5MB)
서버 CPU ............ avg 5.1% p95 24.7% max 30.4%   RSS 164.8 → 172.9MB (종료 후 160.7)
```

- 제출 지연 목표(p95 < 2s)를 두 자릿수 ms 로 통과. 단, 이 수치는 "표 → 첫 poll:update" 근사치(README 해석 주의)이며 브로드캐스트 큐 적체가 없었다는 것은 `poll_settle_ms` 가 창 길이와 같다는 점이 보증한다.
- 수신 5.5MB/200명 = 참가자 1인당 27KB. 이 브랜치의 `pollDistribution` 은 비공개 상태 참가자에게 `total` 만 보내므로(익명·after_close 모델) 현황 문서의 "1인당 2.8MB" 최악 사례보다 훨씬 작다. 공개(live) 정책 + 워드클라우드 entries 포함이면 n² × 평균 7KB 가 된다 → p2-core 의 room 분리가 담당.

## 3. PDF 전송 경로 개선 (리스크 3)

### 변경

| 항목 | 이전 | 이후 |
|---|---|---|
| 업로드 | 정규식 페이지 수 추정 → `layout:'pdf'` 슬라이드 | 서버가 `pdfjs-dist`(legacy build) + `@napi-rs/canvas` 로 **페이지별 webp 사전 렌더**(긴 변 1920px, 품질 80) → `layout:'image'` 슬라이드. `pdfUrl`·`pageNumber` 는 출처로 보존 (편집기의 PDF 텍스트 추출, 삭제 시 원본 정리) |
| 렌더 위치 | (참가자 브라우저) | `worker_threads` 워커(`server/src/pdf/render-worker.mjs`) — 메인 이벤트 루프를 막지 않음, 동시 2개 제한(`PDF_RENDER_CONCURRENCY`), 5분 타임아웃, 페이지 상한 500 |
| 폴백 | — | 암호화·손상 등 렌더 실패 시 기존 `layout:'pdf'` 슬라이드 생성(레거시 경로 유지). 기존 PDF 덱은 그대로 동작 |
| `/api/uploads/*` | `readFileSync` 전량 버퍼, PDF 캐시 헤더 없음 | `createReadStream` 스트림, `Cache-Control: public, max-age=31536000, immutable`, `ETag`(+`If-None-Match` → 304), `Accept-Ranges` + 단일 Range 206, 파일명 화이트리스트(경로 이탈 차단) |
| pdf.js | cdnjs 3.11 `<script>` + 워커 cdnjs | `pdfjs-dist` 4.10 을 Vite 로 자체 번들(`client/src/lib/pdfjs.ts`, 워커 `?url`). 레거시 pdf 슬라이드·편집기에서만 지연 로드 → 초기 번들 불변, 사내망 CDN 차단 무관 |
| Dockerfile | — | `fonts-noto-cjk` 설치(임베드 안 된 한글 폰트 대체). `@napi-rs/canvas` 는 linux-x64-gnu prebuilt 라 네이티브 빌드 도구 불필요 |

### 효과 (400명 강연, 40p 덱 기준 계산)

| | 이전 | 이후 |
|---|---|---|
| 참가자 1인 입장 시 다운로드 | 원본 PDF 전체(예: 30MB) + pdf.js 워커 1.4MB(cdnjs) | 현재 페이지 webp 1장 (실측 12KB/장, 사진 위주 슬라이드는 100~200KB) |
| 400명 입장 이그레스 | 12GB | 5~80MB |
| 페이지 이동 | `getDocument` 재호출(캐시 헤더 없음) | `<img>` 1장, 1년 immutable 캐시라 되돌아가면 재요청 없음 |
| 서버 메모리 | 요청당 30MB 버퍼 × 동시 요청 | 스트림(64KB 청크) |

실측: 40p 업로드 총 6.0s(렌더 5.6s), 검증용 2p PDF 1.0s. 렌더는 워커 스레드라 그 사이 소켓 처리에 영향이 없다(별도 측정은 안 함).

## 4. 한계와 다음 단계

1. **N=200 은 목표(400~1,000)의 하한**이다. 1,000명은 k6 VU 1,000 + 소켓 1,000 이 한 PC 에서 돌아 k6 쪽이 먼저 병목이 될 수 있으므로 별도 머신 또는 `k6 cloud`/분산 실행이 필요하다. 스크립트는 `-e N=1000` 만 바꾸면 된다.
2. 이 수치는 **브로드캐스트 재설계 전 기준선**이다. p2-core(room 분리·500ms 배치·rate limit) 병합 후 같은 스크립트로 재측정해 `poll_update_frames` 가 n² 에서 n×(창/500ms) 수준으로 줄었는지, `vote_ack_latency` 가 배치 창(≤500ms) 안에 머무는지 확인해야 한다. rate limit 브랜치에서는 강의실 생성 20/분 때문에 연속 실행 시 1분 대기.
3. join 지연의 바닥은 Supabase 왕복(≈110ms)이다. 입장 스파이크에서는 `persistParticipant` 를 `joined` 응답 뒤로 미루거나 배치 upsert 로 바꾸는 것이 다음 개선점(현황 문서 §2.4 A).
4. CI 게이트: `k6 run --summary-export` 종료 코드로 임계값 위반을 잡을 수 있다. GitHub Actions 에서는 `grafana/setup-k6-action` + 서버 컨테이너 기동 후 `N=300` 정도가 러너 한 대에서 현실적이다.
5. PDF 렌더 품질: 1920px 고정이라 4K 프로젝터에서는 약간 소프트하다. 필요 시 `maxLongEdge` 2560 + 품질 85 로 올리면 장당 2~3배 용량. 폰트가 임베드되지 않은 한글 PDF 는 Docker 이미지의 Noto CJK 로 대체 렌더되며, 로컬 Windows 는 시스템 폰트를 쓴다.
